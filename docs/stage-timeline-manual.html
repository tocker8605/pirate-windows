03문서 구조와 시간 단위

루트에는 schema_version: 2, time_unit: "seconds", events 배열이 필요합니다. 다음은 문법 설명용 예제이며, 실제 스테이지 전체를 대체하기 위한 파일은 아닙니다.

{
  "schema_version": 2,
  "time_unit": "seconds",
  "events": [
    {
      "at": 0.9,
      "action": "banner",
      "name": "mission"
    },
    {
      "at": 2.75,
      "action": "spawn",
      "definition_id": 1,
      "position": [
        80,
        -50
      ],
      "pattern": 1011
    },
    {
      "at": 2.75,
      "action": "spawn",
      "definition_id": 1,
      "position": [
        270,
        -50
      ],
      "pattern": 1011,
      "overrides": {
        "hp": 50
      }
    }
  ]
}
  • at은 스테이지 시작부터 흐른 시간입니다. 60초는 60, 100ms는 0.1입니다. 0.9초 격자에 맞출 필요가 없습니다.
  • 게임은 60Hz로 처리하므로 이벤트는 지정 시각을 지난 첫 처리 틱에 실행됩니다. 일시 정지 중에는 스테이지 시간이 진행되지 않습니다.
  • 이벤트는 수가 정해진 고정 배열 슬롯이 아닙니다. 과거의 약 200개 타임라인 제한이나 틱당 5개 등장 제한은 없습니다. 과도한 동시 등장은 여전히 성능과 난이도를 고려해야 합니다.
  • JSON은 큰따옴표를 사용합니다. 설명은 아래의 comment 필드로 작성합니다. //·/* */ 주석 문법, 마지막 항목 뒤 쉼표, NaN, Infinity는 사용하지 마십시오. 숫자를 "2.75"처럼 문자열로 쓰면 안 됩니다.
이벤트는 로드할 때 at 오름차순으로 자동 정렬되며, 같은 at은 파일의 순서를 유지합니다. 숫자가 아닌 at이나 음수 등 검증 오류가 있으면 해당 타임라인은 빈 목록으로 로드됩니다. 보스가 나오지 않는 경우 먼저 오류 로그를 확인하십시오.

설명을 남기는 comment 필드

파일 전체와 모든 이벤트에 선택적으로 comment 문자열을 넣을 수 있습니다. 게임 실행에는 영향을 주지 않습니다. 여러 줄 설명은 문자열 안에서 \n으로 구분하십시오.

{
  "schema_version": 2,
  "time_unit": "seconds",
  "comment": "1면 초반 편대 구성 메모",
  "events": [
    {
      "at": 10,
      "action": "spawn",
      "definition_id": 1,
      "position": [120, -50],
      "pattern": 1011,
      "comment": "첫 편대 / 왼쪽 진입"
    }
  ]
}

설명용 예제입니다. events 배열에서 at 없는 객체는 모두 무시합니다. 그룹 앞에 {"comment":"편대 좌측1"} 또는 {"action":"memo","comment":"편대 좌측1"}를 넣고 빈 줄로 구분할 수 있습니다. memo는 실행 액션이 아닙니다. at: null처럼 at이 있는 항목은 기존 검증을 받습니다.

04지원하는 이벤트는 세 가지입니다

spawn · 적 한 대 생성

필드값 / 의미
at0 이상의 유한한 숫자. 초 단위 등장 시간.
action"spawn"
definition_id적 정의표에 존재하는 정수 ID. 이름 문자열이 아닙니다.
position[x, y] 숫자 두 개.
pattern이동 패턴 번호. 생략 시 0이지만, 의도한 패턴을 명시하는 것을 권장합니다.
overrides선택. {"hp": 50}만 지원. 양수 HP로 이 개체의 현재·최대 HP를 함께 설정합니다.

기본 HP는 data/enemies.json에 있습니다. 같은 적 모두의 HP를 바꾸려면 정의표를 수정하고, 특정 등장 개체만 바꾸려면 overrides.hp를 사용하십시오. hp를 spawn 바로 아래에 적는 형식은 지원하지 않습니다.

고정 포대의 start_exposed는 true이면 처음부터 노출, false 또는 생략이면 숨김 상태로 등장 후 Y>80에서 전개합니다. 숫자 0/1 대신 불리언을 사용하십시오.

scroll · 배경의 목표 속도와 반복 경계 변경

{"at": 30, "action": "scroll", "mode": 2, "speed": 100}

mode는 1·2·3 중 정수, speed는 0 이상의 숫자이며 단위는 픽셀/초입니다. 목표 속도로 서서히 접근합니다. 자세한 구획 연결 규칙은 09절을 참고하십시오.

banner · 화면 메시지

{"at": 0.9, "action": "banner", "name": "mission"}
{"at": 99.9, "action": "banner", "name": "warning"}

이름은 소문자 mission 또는 warning만 지원합니다. 기본 표시 시간은 2.4초이며, 보스가 등장하면 진행 중인 배너가 지워집니다. WARNING을 표시한다고 보스가 자동 생성되지는 않습니다.

count, repeat, interval, velocity 등 정의되지 않은 이벤트 필드를 추가하면 오류입니다. 여러 대는 spawn을 여러 줄 작성하십시오. 탄종·발사 주기·스프라이트를 timeline 필드로 바꾸는 기능은 없습니다.

5면 고정포대 배치

ID 51: 기관포, 52: 에너지포. 미사일 고정포대(ID 53)는 삭제되었습니다. start_exposed는 true/false 불리언입니다. true는 처음부터 노출, false 또는 생략은 숨김 상태입니다. 숨은 포대는 Y가 80을 넘으면 0.8초 동안 솟아오르며, 완전히 나온 뒤에만 피격됩니다. pattern 대신 배경의 실제 스크롤을 따릅니다. 파괴 잔해도 배경 바로 위에서 스크롤됩니다.

{"at": 2, "action": "spawn", "definition_id": 51, "position": [75,-60], "start_exposed": false}

05좌표와 동시 등장 편대

논리 화면은 400 × 480입니다. 창을 확대해도 타임라인 좌표는 바뀌지 않습니다. X는 오른쪽, Y는 아래쪽으로 증가합니다.

일반 적의 위치는 대체로 스프라이트 좌상단 기준입니다. 보스 본체는 X가 중심이고 Y가 위쪽 기준입니다. 그림의 여백·draw_offset·파츠 부착 오프셋 때문에 숫자와 보이는 중심이 다를 수 있습니다.

화면 밖 좌표도 유효합니다. 위에서 진입은 y=-50, 왼쪽 진입은 x=-50, 아래에서 상승은 y=480 등이 가능합니다. 진입 위치와 이동 패턴을 함께 선택해야 합니다.

동시에 두 대를 등장시키려면

{"at": 8, "action": "spawn", "definition_id": 1, "position": [80, -50], "pattern": 1011},
{"at": 8, "action": "spawn", "definition_id": 1, "position": [270, -50], "pattern": 1011}

50픽셀 폭의 적이라면 X=80과 270은 좌상단 좌표 기준으로 화면 중앙을 사이에 둔 대칭 예입니다. 모든 적에 X=100 / 300을 넣으면 그림 폭 때문에 시각적 대칭이 아닐 수 있습니다. 위 두 줄은 events 배열 안에 삽입하는 조각입니다.

07이동 패턴 번호 참조

패턴은 초기 위치·현재 속도·주인공 위치에 따라 결과가 달라지는 규칙입니다. 일부는 진행 중 다른 번호로 전환됩니다. 보스용 번호를 일반 적에 적용하는 용도로 쓰지 마십시오.

24014면 중앙 코어 전용 모듈일반 이동 패턴이 아닙니다. ID 133과 함께 사용합니다.

번호만으로 관리되지 않는 전용 동작

  • 보스 본체 91~94: 본체 전용 이동·공격 코드가 동작합니다. 현재 timeline의 pattern은 0입니다.
  • 3면 구체 123·124: boss_orb_motion.gd가 이동합니다. 초기 위치 (100,100) / (300,100)에 정착하고, 본체 HP가 절반 아래가 되면 Y=240으로 이동하면서 본체 X−35 / X+35를 추종합니다. Y 이동 중에는 발사하지 않습니다.
  • 4면 중앙 코어 133: pattern 2401과 boss_core_motion.gd를 함께 사용합니다. HP 200 이하에서 위로 사출한 뒤 화면 중심 (200,240)으로 이동·고정하는 전용 동작입니다.
엔진의 timeline 검사에서 pattern은 숫자인지만 검사합니다. 잘못된 번호가 파일 로드를 통과해도 실제 플레이에서 Unknown enemy movement pattern 오류가 날 수 있습니다. 아래 검사기는 알려지지 않은 번호를 추가 경고합니다.

09배경 구획과 스크롤

mode는 배경을 해당 번호로 즉시 바꾸는 명령이 아니라, 어디까지 진행하고 어디에서 반복할지 정하는 경계 모드입니다. mode만 바꿔도 현재 배경 위치에 따라 전환까지 시간이 걸립니다.

모드일반적인 역할
1첫 구획 반복 유지.
2첫 구획을 지나 중간 구획으로 진행하고 중간 반복 유지.
3마지막 구획으로 진행하고 마지막 구획 반복 유지.

speed는 목표 속도입니다. 현재 속도가 약 222.22 픽셀/초²의 변화율로 목표에 접근하므로 speed: 0도 즉시 정지가 아닙니다. 배경 전환 시점은 누적 스크롤 거리와 속도 이력의 영향을 받습니다.

스테이지순서
1면바다 → 해안 → 숲
2면녹색 계곡 → 설산 → 산림 능선
3면밤의 설원 → 야간 전초기지 → 밤바다
4면지구 전경 → 우주 → 달 표면 → 달 지하
일반 4면은 예외입니다. 시작부터 mode 2, 속도 약 66.67 픽셀/초로 지구 전경을 한 번 통과하고 우주 구획에서 반복합니다. 이후 mode 3으로 진행하면 달 표면을 통과해 달 지하 반복으로 이어집니다. 4구획이라고 mode 4를 쓰면 안 됩니다. 보스러시 4면은 같은 배경 리소스를 쓰지만 현재 초기 스크롤 설정은 일반 4면과 다릅니다.

10파워 / HP 보급기는 timeline에서 편집하지 않습니다

supply_director.gd가 일반 모드에서 별도로 배정합니다. 보급기 ID 19, 20, 201, 202를 timeline에 넣으면 검증 오류입니다.

  • 일반 1면: 파워 보급기 3회, HP 보급기 3회.
  • 일반 2~4면: 스테이지 시작 파워가 1 / 2 / 3 / 4 이상이면 파워 보급기 총 6 / 5 / 4 / 3회. 시작 1초 뒤 1회가 이 총횟수에 포함됩니다.
  • 나머지 정규 보급은 시작 10초 후 ~ 첫 보스 등장 10초 전 사이에 무작위 배정됩니다. 구간을 나누고 종류를 섞어 한때 몰리지 않도록 합니다. 등장 X는 100~300, Y는 480입니다.
  • 생존 상태에서 실제 피격 시 30% 확률로 추가 HP 보급기가 즉시 등장하며, 성공한 추가 보급은 스테이지당 최대 1회입니다. 일반 보스전과 보스러시에도 적용됩니다.
  • 보스러시: 정기 보급은 없으며, 위의 피격 시 추가 HP 보급만 적용됩니다. 파츠 파괴 시 의도된 파워 아이템 드롭은 별개로 유지됩니다.
  • 현재 파워 아이템은 파워 +1(최대 7), 에너지 +50(최대 100)입니다. HP 아이템은 HP +25(최대 100)입니다.
첫 보스를 20초 이내로 당기거나 본체 spawn을 없애면 정규 무작위 보급 구간이 사라집니다. 이 경우 2면 이후 1초의 파워 보급만 별도로 남을 수 있습니다. 보스 시간을 변경한 뒤에는 보급 횟수도 확인하십시오.

11저장, 확인, 실행 파일 반영

프로젝트에서 테스트

  1. VS Code에서 Ctrl + S로 저장합니다.
  2. 아래 검사기에서 문법과 필수 필드를 확인합니다.
  3. 실행 중인 게임을 완전히 종료하고, 설정된 Godot Tools의 F5 또는 Godot 편집기의 프로젝트 실행으로 다시 시작합니다.
  4. 대상 스테이지에서 등장 위치·이동·탄 패턴·보스/파츠·배경 연결·보급을 확인합니다. 창 크기가 아닌 400×480 논리 좌표 기준으로 조정하십시오.

엔진 로그의 event 0은 events 첫 번째 항목입니다. 번호가 0부터 시작합니다. JSON 문법 오류는 파일 경로와 줄 번호, 스키마 오류는 이벤트 번호와 사유가 출력됩니다.

기존 EXE에 반영하려면 다시 빌드

배포본의 데이터는 PCK에 들어 있습니다. 프로젝트의 JSON을 고치거나 EXE 옆에 JSON을 두는 것만으로 기존 배포본이 바뀌지는 않습니다. 프로젝트 터미널에서 다음 명령으로 빌드합니다.

Set-Location -LiteralPath 'E:\CodexWork\Pirate-II-Godot'
& .\tools\build.ps1 -Godot 'E:\Godot\Godot_v4.7.2-stable_win64_console.exe'

결과물은 build\Pirate-II.exe와 build\Pirate-II.pck입니다. 둘을 같은 폴더에 보관하십시오.

현재 회귀 테스트에는 기존 이벤트 수와 기준 플레이 결과가 포함됩니다. 의도한 타임라인 변경도 기존 기준과 달라 테스트가 실패할 수 있습니다. 문법·플레이 문제가 없는지 먼저 확인하고, 콘텐츠 변경으로 인한 기준 차이는 별도로 검토해야 합니다. 실패를 전부 정상으로 간주하거나 기준 데이터를 무조건 지우지 마십시오.
검증을 마친 편집본을 테스트 생략으로 빌드해야 하는 경우
& .\tools\build.ps1 -Godot 'E:\Godot\Godot_v4.7.2-stable_win64_console.exe' -SkipTests

-SkipTests는 회귀 테스트 실행만 생략합니다. JSON을 자동 수정하거나 게임 동작의 올바름을 보장하지 않습니다. Godot import 및 export 오류 검사는 계속 실행됩니다.

12JSON 검사 연습장

수정한 JSON 전체를 붙여넣거나 파일을 선택하십시오. 문서 작성 시점의 적 정의표와 규칙으로 검사합니다. 실제 게임 실행 검증을 대신하지는 않습니다.

예제는 v24.42 스냅샷입니다.

🟩 일반 적·파츠🟨 보스 본체🟦 스크롤🟥 메시지선 위에 마우스를 올리면 시각을 볼 수 있습니다.

검사기는 원본 파일을 수정하거나 업로드하지 않습니다. 게임 로더는 at 기준으로 안정 정렬합니다. 게임보다 엄격한 정수 권장 검사와 알려진 패턴 경고가 포함되어 있습니다. 공격·전용 이동·성능·화면상의 자연스러움까지 판정하지는 않습니다.
